# 02 — Product, UX & Frontend Rules

## Product rules

1. Debug Dojo teaches debugging; it does not default to showing complete solutions.
2. The execution result is determined by the runner, not generated by the LLM.
3. A submission has one of four test outcomes: `passed`, `wrong output`, `runtime error`, or `timeout`.
4. Hidden tests remain hidden in every screen, toast, browser payload, and error state.
5. A recurring mistake is only confirmed when the same category appears on at least two different challenges.
6. A challenge recommendation must include a reason tied to observed learner behavior.
7. A pass without hints is stronger evidence of mastery than a pass after hints.
8. Use pseudonymous learner IDs; do not ask for real student personal data.

## Frontend rules

- Keep UI components focused and reusable.
- Use TypeScript types for API responses and challenge metadata.
- Keep API access in a service layer, not scattered throughout components.
- Represent loading, empty, error, success, and disabled states explicitly.
- Disable duplicate submissions while a request is in progress.
- Show clear labels on actions: “Run code”, “Submit solution”, “Get next hint”.
- Do not show a “passed” state before the server confirms it.
- Use inline messages for persistent or contextual errors; use toast notifications for brief confirmations.
- Never put API keys or secrets in frontend environment variables exposed to the browser.
- Do not trust client-provided outcome labels, mistake tags, mastery scores, or hint safety decisions.
- Do not render raw stack traces from hidden tests.
- Sanitize or safely render user-submitted text and code; do not inject it as HTML.
- Keep keyboard navigation and focus states functional.
- Do not use color alone to distinguish test outcomes; pair color with text and/or icons.

## AI and solution rules

- Never send hidden inputs or expected outputs to the browser.
- Do not reveal full solutions in hints.
- If the user requests a solution, follow the product's staged policy in `11-solution-policy.md`.
- The frontend can display only the hint/solution level authorized by the backend.
- Treat AI output as untrusted content; render it as text/Markdown using a safe renderer.

## Toast rules

Use Sonner for concise, non-blocking messages:
- “Code submitted”
- “Hint unlocked”
- “Progress saved”
- “Could not connect. Try again.”

Do not use a toast as the only location for a critical explanation. Do not display sensitive runner details in toasts.

## Code review checklist

- Is the component doing one job?
- Are loading and error states handled?
- Are hidden test details excluded?
- Are interactions keyboard accessible?
- Is the API response validated before rendering?
- Are visual styles using shared tokens?
