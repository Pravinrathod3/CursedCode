Debug Dojo
A coding coach that helps you find the bug without handing you the answer. AI-powered

The story
Rohan is in his first semester. His function should return the total of the last k marks in a
list. It works on all three of his examples. The practice site says: Wrong Answer on test 5.
Test 5 is hidden. Yesterday the site showed him IndexError: list index out of range, which
told him where his program died but not why. So he does what everyone in his hostel does:
pastes the question into a chatbot, copies the answer and submits. Accepted.
Next week the exam has the same kind of loop, and there is no chatbot in the exam hall.
Rohan never needed the answer. He needed someone to point him to the right place to
look, then a little more if he was still stuck, and next week a new problem that makes him
face the same mistake until he stops making it.
Problem overview
Beginners learn programming by writing code and reading what goes wrong, but feedback
is often hard to use. A traceback names an error without explaining it, and a program can
run and still give the wrong answer. Tools that report only pass or fail don't show where to
look; tools that give full answers too early remove the struggle that makes learning stick.
And running learner code is risky: code from an unknown author must not read sensitive
files, reach the network or consume unlimited resources.
Build a practice environment that runs learner code safely, explains failures in plain
language, gives hints that get more specific without giving the answer away, and learns
which mistakes each learner keeps making.
The challenge
Build a practice environment for one programming language your team can support well.
Every submission must do all of the following:
1. Challenges. At least 10 challenges across at least 3 difficulty levels and at least 4
concepts. Each has a description, starter code, concept tags, at least 3 visible tests
and at least 5 hidden tests, including edge cases. Your set must include the four judge
challenges below, exactly as specified.
Page 1 of 6
2. Restricted execution. Learner code never runs unrestricted. Full sandboxing is not
required; a constrained local test runner is acceptable, and stronger isolation scores
higher.
3. Per-test outcomes. Report every test separately as exactly one of: passed, wrong
output, runtime error or timeout. A run killed by a memory, output or disk limit counts
as a runtime error and says which limit.
4. Hidden tests stay hidden. Never reveal a hidden test's input, expected output, the
program's output on it or its exception message. An explanation may name the kind of
input involved ("a case where k is larger than the list"), never the values.
5. Plain-language explanations. When a submission fails, explain the failure in plain
language to help the learner find the problem.
6. Progressive hints. Offer a ladder of at least 3 hints per failure, each more specific than
the last. No hint, including AI-generated ones, may reveal the complete solution, even
when the learner asks for it.
7. Recurring mistakes. Tag each failed submission with mistake categories. Your
taxonomy must include these five, kept distinct, and may add more: off_by_one,
unhandled_short_input (empty or too-short input), print_not_return,
boundary_comparison (such as < for ≤) and mutates_input. A category is recurring
once it appears in at least 2 different challenges. Show it to the learner, and choose or
generate the next challenge to practise it, saying why.
8. Skills by concept. Keep a mastery estimate per concept, updated from the learner's
work. A pass without hints counts for more than a pass after hints.
9. Judge interface. Expose POST /api/submit, taking {learner_id, challenge_id, code} and
returning the outcomes and the explanation as JSON in the shape shown in the
Example; POST /api/hint, taking {submission_id} and returning the next hint; and GET
/api/learner/{learner_id}, returning the learner's recurring mistakes, mastery per
concept, and the next challenge with the reason.

A good hint ladder for it:
1. Your three examples never ask for more marks than the list holds. What should
last_k_total return when k is bigger than the list?
2. Work out last_k_total([2, 5], 3) by hand. Which index does your loop start at, and what
does marks[-1] mean in Python?
3. In Python a negative index counts back from the end, so some marks get added twice.
Your start index must never go below 0.
4. Python has a built-in that returns the larger of two numbers. Use it to work out the
start index once, before the loop.
No hint contains code, and the learner still writes the fix.
Rules
Language and stack: one programming language for learners; any stack for the
platform.
Challenge content: write your own, or adapt openly licensed sources with attribution.
Write your own hidden tests.
AI: any model orAPI may write explanations and hints. Log every prompt and response;
judges may ask to see them.
Learner data: pseudonymous accounts only. No real student data.
